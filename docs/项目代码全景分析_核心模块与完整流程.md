# VoiceInk 项目代码全景分析（中文）

> 目标：回答“除了 LLM 调用外，这个项目还有哪些特别实现模块，它们如何协同工作”，并给出一个可复现的完整案例（从按下快捷键到粘贴文本）。

## 1. 项目定位与总体架构

VoiceInk 本质上不是“单一的语音转文字调用器”，而是一个**围绕录音-转写-增强-粘贴**闭环构建的 macOS 原生生产力系统。其核心特征是：

- 本地/云端/流式 多模型统一接入（不是绑定某一个 ASR/LLM）。
- 录音生命周期与 UI、快捷键、系统权限、媒体控制深度耦合。
- “Power Mode”按应用/URL自动切换配置，形成上下文感知工作流。
- 结果输出不是简单显示，而是自动粘贴、可选自动发送、可恢复剪贴板。
- 历史记录、清理策略、模型预热、启动恢复等工程能力完善。

## 2. 关键模块（除“调用 LLM”之外）的特别实现

### 2.1 应用启动与依赖装配（Composition Root）

在 `VoiceInkApp` 中完成核心依赖注入与容错：

- SwiftData 容器采用“持久化失败 -> 内存降级 -> 最小容器兜底”三级策略。
- 启动时集中构建 `WhisperState`、`HotkeyManager`、`AIEnhancementService`、`ActiveWindowService`、`MenuBarManager`。
- 启动即接入自动清理、更新检查、公告服务。

这说明项目在工程层面优先保证“可运行”和“可恢复”，而不是把失败直接抛给用户。

---

### 2.2 录音引擎：设备切换 + 媒体协同 + 实时电平

`Recorder` 模块有几个很有价值的细节：

1. **设备热切换**：监听 `audioDeviceSwitchRequired`，录音中可重配设备，失败则安全停止并通知。  
2. **系统媒体协同**：开始录音时暂停媒体并静音系统，结束后恢复，减少串音与回声影响。  
3. **无声音提醒机制**：录音后第 5s 与 12s 检查是否检测到有效音频，主动提醒用户。  
4. **音频电平平滑**：对平均/峰值做 EMA 平滑（约 17ms 刷新），保证 UI 观感稳定。

这部分体现了“可用性工程”，不是单纯调用音频 API。

---

### 2.3 转写会话抽象：Streaming 与 File-Based 统一协议

`TranscriptionSession` 协议将转写分成：

- `prepare(model)`：流式场景返回音频 chunk 回调。
- `transcribe(audioURL)`：统一返回最终文本。
- `cancel()`：中止并释放资源。

实现层分为：

- `FileTranscriptionSession`：录完上传（批处理）。
- `StreamingTranscriptionSession`：边录边送，若流式失败自动回退到批处理。

**特别实现点：** 流式失败不致命，自动 fallback；同时对“仅流式模型”提供 batch 兼容模型映射（由 `TranscriptionServiceRegistry` 处理），显著提升稳定性。

---

### 2.4 服务注册中心（多模型统一路由）

`TranscriptionServiceRegistry` 将 provider 与具体服务解耦：

- local -> `LocalTranscriptionService`
- parakeet -> `ParakeetTranscriptionService`
- nativeApple -> `NativeAppleTranscriptionService`
- 其他云端 -> `CloudTranscriptionService`

并且支持：

- 自动判断模型是否支持 streaming。
- 对不兼容的流式模型自动选择批处理替代模型。

这使 UI 和上层流程只关心“当前模型”，而不关心“这个模型背后怎么接入”。

---

### 2.5 Power Mode：按前台应用/浏览器 URL 自动套配置

这是项目最“产品化”的模块之一：

1. `ActiveWindowService` 获取前台应用。  
2. 若是浏览器，则 `BrowserURLService` 调 AppleScript 读当前 tab URL。  
3. 从 `PowerModeManager` 按 URL -> App -> Default 逐级匹配配置。  
4. `PowerModeSessionManager` 在 session 级保存原状态（AI开关、Prompt、模型、语言等），应用临时配置，结束时回滚。

**价值：** 用户在不同场景（邮件、代码、社交媒体）可自动切换不同转写与增强策略，减少手动切换。

---

### 2.6 Prompt 触发词自动切换（语音中内嵌指令）

`PromptDetectionService` 会在转写文本中识别触发词（前缀/后缀，且处理标点边界），并：

- 临时开启 AI 增强（如果原本关闭）。
- 自动切换到指定 Prompt。
- 移除触发词后再送入增强。
- 完成后恢复用户原设置。

这实现了“语音命令式 Prompt 切换”，不用手工点 UI。

---

### 2.7 文本后处理流水线（高可控）

在 `WhisperState.transcribeAudio` 中，文本会经过一系列管线：

1. `TranscriptionOutputFilter`：去 hallucination 样式噪声（括号块、标签块）、可选去口头语。  
2. `WhisperTextFormatter`：可选格式化。  
3. `WordReplacementService`：自定义词替换（支持逗号多变体、区分有空格语言与 CJK/Thai 非空格语言）。

这使最终输出更接近“可直接提交/发送”的文本，而不是原始 ASR 字串。

---

### 2.8 粘贴与自动发送：输入法兼容的工程细节

`CursorPaster` 不是普通“写剪贴板+Cmd+V”而已，它会：

- 可选保存并恢复原剪贴板内容。
- 粘贴前尝试切到 QWERTY 输入源（ABC/US），避免某些输入法下虚拟键位导致 Cmd+V 失效。
- 粘贴后恢复输入源。
- Power Mode 开启 `isAutoSendEnabled` 时，粘贴后自动发送 Enter。

这解决了跨应用自动输入常见的稳定性问题。

---

### 2.9 快捷键系统：不仅是“一个热键”

`HotkeyManager` 同时支持：

- 双热键配置。
- 修饰键长按/短按逻辑（hands-free 与 push-to-talk 区分）。
- 自定义快捷键（KeyboardShortcuts）。
- 中键按压延迟触发。
- 粘贴上一次转写/增强结果、重试上一次转写、打开历史窗口。

这让“输入流程”更接近专业 dictation 工具。

---

### 2.10 数据生命周期治理（隐私/存储）

`TranscriptionAutoCleanupService` 支持：

- 按保留分钟数清理旧转写 + 对应录音。
- 立即删除模式（零保留）。
- 扫描并删除无引用 orphan 音频文件。

这对隐私合规和长时间运行的磁盘占用控制很关键。


## 3. 一条完整案例（从按键到文本发送）

下面给一个“真实可发生”的完整业务链路：

### 场景

- 用户在 Chrome 打开 Gmail。  
- 设置了 Gmail URL 对应 Power Mode：
  - 转写模型：Deepgram `nova-3`（支持 streaming）
  - 启用 AI 增强
  - 指定邮件润色 Prompt
  - 自动发送开启
- 用户按住全局热键开始说话，最后松开。

### 步骤推演（对应代码行为）

1. **热键触发** `WhisperState.toggleRecord()` 进入 start 分支。  
2. 先创建永久 wav 文件路径，`Recorder.startRecording` 立即开始录音（不等网络）。  
3. 并行执行 `ActiveWindowService.applyConfiguration()`：检测前台 Chrome，调用 `BrowserURLService` 读取当前 URL，命中 Gmail 配置，`PowerModeSessionManager.beginSession` 应用配置。  
4. `TranscriptionServiceRegistry.createSession(for: model)` 因 `nova-3` 支持流式，创建 `StreamingTranscriptionSession`。  
5. `session.prepare(model)` 返回音频 chunk 回调；此前缓存的 chunk 被 flush 给流式服务，实现“先录后连”的无损衔接。  
6. 用户结束录音，再次触发 `toggleRecord`：停止录音，构建 `Transcription` 数据对象并进入 `transcribeAudio`。  
7. 优先走 session 的 `transcribe(audioURL)`：若流式成功，直接返回最终文本；若失败自动 fallback 批处理。  
8. 文本后处理：OutputFilter -> 格式化 -> 词替换。  
9. 若增强可用：
   - 先做触发词检测（可动态切 Prompt）。
   - 调用 `AIEnhancementService.enhance`（带 rate limit 与重试退避）。
10. 保存转写记录并发出 `transcriptionCompleted` 通知。  
11. `CursorPaster.pasteAtCursor` 将最终文本粘贴到 Gmail；因配置自动发送，随后 `pressEnter()` 发信。  
12. 若触发词改变了 AI 设置，`PromptDetectionService.restoreOriginalSettings` 回滚；最后关闭 mini recorder。

该链路展示了 VoiceInk 的核心竞争力：**流程编排能力**，而不只是某个模型 API 调用。


## 4. “为什么这个实现是特别的”——工程视角结论

1. **高鲁棒性**：流式/批处理双通路 + 自动回退。  
2. **低等待感**：录音先行、模型和上下文并行准备。  
3. **高上下文感知**：前台应用+URL 触发配置切换。  
4. **高可控输出**：过滤、格式化、替换、增强可组合。  
5. **系统级可用性**：输入法兼容粘贴、媒体暂停恢复、自动清理。  
6. **可扩展架构**：service registry + session abstraction，使新增 provider 成本较低。

## 6. 给二次开发者的落地建议

- 若要新增转写 provider：优先在 `TranscriptionServiceRegistry` + `TranscriptionSession` 扩展，避免把 provider 逻辑塞进 `WhisperState`。  
- 若要新增“语音指令”：复用 `PromptDetectionService` 的触发词解析框架，不要在 UI 层直接硬编码。  
- 若要提升企业安全：可基于 `TranscriptionAutoCleanupService` 增加“启动即清空策略”与“导出审计日志”。  
- 若要做垂直场景（客服/医生/法务）：优先强化 `WordReplacementService` 与 Prompt 模板，而不是先改核心转写管线。
